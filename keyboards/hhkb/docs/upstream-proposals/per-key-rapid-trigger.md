# Proposal: per-key Rapid Trigger, per-key actuation point and a bottom dead zone

## Summary

My fork ([blandjelly/dmk](https://github.com/blandjelly/dmk), branch `feat/hhkb-per-key-rt`) adds
per-key Rapid Trigger and actuation settings to the HHKB port, set from VIA. I use them daily on a
Hybrid ANSI (AHUX01) over USB. I'd like to know whether you would accept them upstream, and in what
form, before I port them onto `dev`.

One part, the **bottom dead zone**, fixes a problem that `dev` still has: with Rapid Trigger on,
a key held at the bottom can release by itself after a few seconds.

## What it adds

All settings are in the existing **HHKB Settings → Rapid Trigger** tab in VIA, plus two generated
tabs with one list per key.

| Setting | Values | VIA id |
| --- | --- | --- |
| Rapid Trigger | `Off`, `All keys`, `Selected keys` | 3 (was on/off) |
| Per-key RT profile | `Default`, `Profile 1`, `Profile 2`, `Profile 3` | per-key tab |
| Per-key actuation point | `Shared` or 0.1-4.5 mm | per-key tab |
| Profile 2 / Profile 3 press and release sensitivity | 0.1-4.5 mm (defaults 0.2/0.2 and 0.5/0.5 mm) | 61-64 |
| Bottom dead zone (RT keys) | 0.0-1.0 mm, default 0.5 mm | 65 |

- **Rapid Trigger mode.** `All keys` behaves like the current on state. With `Selected keys`, only keys
  given a profile use Rapid Trigger; the others use the classic actuation point and release
  hysteresis. Example: RT on WASD only, normal typing on the rest of the board.
- **Profiles.** Profile 1 uses the existing shared press/release sensitivity. Profiles 2 and 3 have
  their own. The top dead zone stays shared.
- **Per-key actuation point.** `Shared` follows the existing **Actuation point**. A value sets the
  point for that key only; on an RT key it is also the depth that arms Rapid Trigger. It is clamped
  like the shared point (above the top dead zone, within the curve's maximum travel).
- Settings belong to the matrix position, not to a keycode, so they apply on every layer.
- A **Per-key summary** label shows how many keys have a profile and how many have their own point.

### Bottom dead zone: fixes held keys releasing by themselves

Once a Topre key bottoms out, the ADC reading follows finger pressure, not travel. Pressing harder
pushes the reading past the calibrated peak; relaxing the finger then drops it by several percent
without any key movement. In Rapid Trigger, `ext` follows that deepest point (in `dev`,
`update_travel` sets `k->ext = v` up to `RT_MAX_PM` 1100), so a key held down with a relaxing finger
moves "up" by more than the release sensitivity and releases. My `[EC]` logs showed held keys
releasing after a few seconds.

The fix caps the deepest point release is measured from at the top of the bottom dead zone:

```c
int16_t bottom = (int16_t)((lut ? lut[125] : RT_FULL_SCALE) - c->bottom_dz * RT_DZ_STEP_PM);
...
k->ext = v > bottom ? bottom : v;   /* deepest point so far */
```

A held key then stays pressed and releases only after moving up by the release sensitivity from the
top of the zone. At 0.0 mm the cap is the calibrated peak. `test_rapid_trigger.c` replays the hardware
log that showed the problem. This part is small and could go upstream on its own, even if the per-key
settings don't.

## Implementation

- `modules/ec/rapid_trigger.c`: profile and per-key actuation handling, bottom dead zone.
- `modules/ec/ec_settings.c`: settings, VIA getters/setters, a per-key profile table that the scan
  reads, rebuilt only after a settings change (`hhkb_settings_mark_dirty()` bumps a revision).
- `modules/ec/classic_matrix.c`: the scan looks up each key's profile in that table; no per-key
  decoding in the scan loop.
- `modules/via_settings/hhkb_via_controls.c`: VIA controls 3 and 61-65, plus the per-key lists.
- `via.json`: the two per-key tabs (ANSI and JIS) are generated by
  `tools/hhkb/generate_per_key_menus.py` from the layouts; `--check` verifies they are current
  (`tests/hhkb_classic/test_per_key_menus.py`). This makes `via.json` much larger (about 10k lines).
- Docs: `via-debug.md` (EN and RU) describe all settings.

**Scan time:** with the [scan changes from the 1000 Hz issue](https://github.com/blandjelly/dmk/blob/feat/hhkb-per-key-rt/keyboards/hhkb/docs/upstream-proposals/scan-1000hz.md), a scan takes the same
time with RT on and off: about 727 µs in `scan_emu.py`, about 850 µs on my keyboard, at 1000 Hz.

**Storage:** per-key settings are in a separate 120-byte EEPROM record at `0x08081700` (version 2).
The firmware writes it only on the first per-key change, and only if the area is empty or already
holds this record; the main settings record is unchanged. `dev` now stores settings in compressed
snapshots (b20e7b2), and its second snapshot uses `0x0808170C-0x080817FF`, which overlaps this record.
For upstream I'd move the per-key settings into the snapshot format instead. That needs your input on the snapshot layout
and its free space.

**Tests** (in `tests/hhkb_classic/`): per-key points and the bottom dead zone in `test_rapid_trigger.c`,
EEPROM round trips and the scan mapping in `test_hybrid_sleep_settings.py`, menus in `test_per_key_menus.py`.

## Hardware status

- Tested: Hybrid ANSI over USB. Press/release sensitivity per profile, per-key points, the bottom
  dead zone and the classic hysteresis behave as configured in `[EC]` logs.
- The release build is in daily use, over USB and over Bluetooth on battery.
- Not tested: Classic, JIS (the JIS tab is generated but unchecked on hardware).
- Flash: in my fork Hybrid builds have only tens of bytes left with GCC 13.2, and Hybrid JIS about
  104 B of RAM. `dev` has more room (with GCC 14, Hybrid ANSI has about 2.5 KB of flash free on `dev`
  against about 1.3 KB in my fork).

Depending on what you prefer:

1. Bottom dead zone only (small, fixes a real problem with RT).
2. Then the RT mode (`Selected keys`), profiles and per-key actuation, with storage moved into the
